# 1人1万イベントの容量確認（2026-09-21）

想定は50人×1万＝50万イベント。今回新たな負荷データの投入や契約変更は行っていない。

## 現在の確認値

- Cloudflare APIでアカウント既定と handoff-research の usage model が `standard` であることを確認。
- D1容量：42,229,760 bytes（Wrangler）、直後のREST確認は43,151,360 bytes。計測時刻差がある。
- Wranglerの過去24時間：read queries 39,932、write queries 19,969、rows read 16,057,796、rows written 226,544。イベント件数とは異なる。
- 購読一覧APIは権限不足403。請求明細・アカウント全体の月間利用残量は確認していない。既存Workers設定と公式のStandardモデルの説明を根拠に評価。
- ブラウザは通常50件／300,000文字以内に分割し約2秒ごとに送信。サーバーは100件上限。json_eachによる一括INSERTで、イベント単位の行を保持。
- 50同時開始・計5,000イベントの保存／再送検証は通過済み。50万イベントを継続送信する試験は未実施。

## 判断

1人1万件という累積件数だけで現在の収集方式を変更する必要はない。50人が30分で50万件を生成すると平均約278イベント／秒、60分なら約139イベント／秒。瞬間的な集中やネットワーク品質で遅延は変わる。

今回の模擬参加のAPI書き出しは1イベント平均565 bytes、50万件なら約283MB。ただしこれはAPIの付加列を含むJSONサイズの単純外挿であり、D1テーブル・インデックスの実容量見積もりではない。長い編集スナップショットの比率が増えれば大きくなる。

Standard側のD1上限は1DB10GB、月間書込5,000万行を含む。50万イベントにインデックス更新・回答・再保存が加わることを考慮しても、この実験規模は十分現実的。ただしアカウント内の他利用を含む月間請求額や、全状況での無損失は保証しない。

無料枠の1日10万行では50万イベントを同日に保存できない。一括INSERTはクエリ数を抑えるが、書込行数の課金単位は減らさない。D1は単一DB内でクエリを順次処理するため、件数と同時書込速度は別の評価軸。

閲覧・書き出しは別問題で、50万件を1つのHTMLに全埋込みすると重くなる。JSON/NDJSONを分割保存し、参加者・日時で絞った一覧にする運用が適する。現行1参加のHTMLは1,458件で確認したもの。
